## 4. Модель данных и функции

Поля задачи: `id` (положительное безопасное целое), `title` (строка длиной от 1 до 100 после `trim`), `completed` (boolean, при создании всегда `false`), `priority` (`"low"`, `"medium"` или `"high"`).

Файлы: `data.js` — исходные наборы, `task-service.js` — девять прикладных функций, `main.js` — демонстрационный сценарий, `checks.js` — готовые проверки.

Функции чтения (`findTaskById`, `getPendingTasks`, `getTaskTitles`, `getTaskStats`) возвращают данные напрямую; при отсутствии задачи — `undefined`. Функции изменения (`addTask`, `setTaskCompleted`, `renameTask`, `removeTask`) возвращают `{ ok: true, tasks }` при успехе и `{ ok: false, error }` при отказе.

**Почему id не равен индексу:** после удаления записи индексы оставшихся элементов сдвигаются, а `id` сохраняется за задачей.

**Почему `getTaskStats` возвращает число, а не строку с процентом:** округление относится к отображению; расчётная функция должна возвращать числовое значение, пригодное для дальнейших вычислений.

**Какие объекты копируются при изменении задачи:** создаётся новый массив и новый объект изменённой записи; остальные объекты переиспользуются.

## 9. Вывод

По сравнению с ПР1 расчёты вынесены в отдельные функции с единым контрактом «успех / ошибка», данные представлены массивом объектов, а операции изменения не мутируют входной массив и его объекты. Возвращаемые значения используются вызывающим кодом: в `main.js` текущее состояние заменяется на `result.tasks` только при `result.ok === true`, поэтому неуспешная операция не портит данные. Неизменность входных объектов подтверждена проверкой 33, в которой массив и объекты предварительно заморожены. Наиболее показательным был эксперимент 2: отсутствие `return` в стрелочной функции приводит к `undefined`, хотя вычисление внутри записано.
